I let AI agents write 94 pull requests. The interesting part is the 21 times they got blocked.

September 2026

Over the last two weeks I built a working SaaS product with AI agents doing most of the typing. That part isn't interesting anymore. Everyone has that post.

Here's the part I haven't seen anyone show: what it takes to make agent output safe to merge, and what happens when you actually enforce it.

The project is frontdesk — an AI request desk for small businesses. A customer submits a question through a public form. The system classifies it, retrieves the business's own documents, and drafts a reply with citations. A human approves, edits, or rejects it. Nothing reaches a customer without that human step.

It's live at frontdesk.jtrent.dev. The repo is public. Every number below is checkable against it.

The ledger

  • 94 merged pull requests, 198 commits, 16 days
  • 52 by an agent running on my VPS, 26 by an agent in my IDE, 14 by Dependabot, 2 by me directly
  • 41 architecture decision records, written before the code they govern
  • 21 blocking reviews across 10 pull requests
  • One PR got blocked 7 times before it merged clean

That last line is the one I'd want to be asked about in an interview.

What a guardrail looks like when it's real

Every PR carries a required label naming who wrote it and a Model: line naming which model. CI rejects the PR if either is missing or ambiguous. Provenance isn't a convention people remember, it's a gate.

Then a review agent reads every diff against a written rubric: tenancy, secrets, architectural drift, whether the PR contradicts a decision record. A finding marked blocking fails a required check. No agent can merge. Only I can.

PR #92 hit that wall seven times. One finding was that the code named a specific cloud vendor inside a layer where a decision record had explicitly said vendor names don't belong. A human reviewer skimming a green diff at 11pm misses that. The agent didn't.

Yesterday it blocked me. Twice.

I'd changed a mechanism a decision record had decided on, and recorded the change by editing that record in place. The repo's own docs say: superseding a decision means a new file, never edit a decided one. I wrote that rule. I broke it anyway. The reviewer quoted my own line back at me and refused the merge until I wrote the superseding record properly.

That's the whole argument. The value isn't that an AI reviews code. It's that the rules get enforced against the person who wrote the rules.

The eval gate caught a bug I'd already shipped

Prompt and retrieval changes run against 20 labeled requests before they can merge. Classification accuracy, recall@5, recall@1. None may drop below a committed baseline, and only a human-labeled PR can raise that baseline — an agent can't move its own goalposts.

The first time it ran, accuracy came back at 0.20.

Not a regression. The model was wrapping its JSON in a markdown code fence, the parser didn't strip it, and four out of five classifications were silently failing. That was in production. The demo looked fine because the fallback path was doing something reasonable.

Two weeks of manual testing hadn't found it. The first automated run did, in about a minute.

The part I think is actually novel

Every six hours, an agent reads production. Prometheus alerts, error-shaped log lines, pod restarts, failed jobs. It does this through a Kubernetes service account that cannot create, patch, exec, or read secrets — I've verified each of those returns no. It has exactly one write capability: open a GitHub issue, with quoted evidence, a hypothesis, a proposed fix, and a confidence level.

It cannot fix anything. That's deliberate. An agent that can restart a deployment at 3am is a liability. An agent that can tell you why you should is an on-call engineer who never sleeps and never guesses at what it saw.

Its instructions live in the repo, so changing what the agent is allowed to do is a pull request that gets reviewed like any other.

The money

$0.0053 per triaged request. $6.49/month for the node. The whole thing runs on one small server.

I priced the alternative: below roughly 6,600 requests a month, renting tokens beats the cheapest box that can run a model locally. Above that, owning the hardware wins. The cost table is in the README with the arithmetic shown, because "it's cheap" isn't an architecture argument and I'd rather be corrected on numbers than believed on adjectives.

What I'd tell someone about to try this

The models are not the hard part. They're good enough. The hard part is that an agent will confidently do something reasonable-looking that violates a decision you made three weeks ago and forgot you made, and it will do it in a diff that passes every test.

So the work isn't prompting. It's building the machinery that makes a violation impossible to merge: decisions written down where agents read them, provenance that can't be omitted, a reviewer with a rubric and the authority to say no, an eval gate an agent can't move, and a human on the merge button.

Five of those six guardrails were enforcing before I wrote this. The sixth, the ops agent, went live this week.

The repo is public, including the pull requests where the guardrails blocked me. Those are the ones worth reading.
